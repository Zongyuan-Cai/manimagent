# 用户记忆与个性化

更新：2026-11-06。当前实现面向本机单用户，使用 SQLite 提交分层用户记忆和后台沉淀状态，同时生成可读的 Markdown 索引、条目文件与任务注入记录。核心行为是生成条目、独立会话支持、短期向深层迁移、纠正与清理；不包含生成器经验。设计理由见[分层记忆设计](../design/05-长期记忆与个性化.md)，后台链路的既有验证见[记忆沉淀验收报告](../../testresult/memory-consolidation-20261106/报告.md)。既有真实记忆与配音证据见[历史全链路报告](../../testresult/memory-20261106/报告.md)，稳定投影与缓存统计见[记忆与缓存修复报告](../../testresult/memory-cache-20261106/报告.md)。

## 网页使用

1. 按[运行与配置](运行与配置.md)启动服务，并配置可用的回答模型。
2. 从顶部“我的偏好”打开独立管理窗口，展开“添加偏好”，填写希望系统记住的表达并点击“生成记忆”。卡片先展示偏好内容和“近期／长期”状态；“详情与来源”中可核对字段、范围、有效期和原句依据。卡片的“近期／长期”分别对应短期与深层记忆，存储和晋升规则不变。模型没有提取到可支持的信息时，不会凭空生成用户画像。
3. 普通“纠正”保留条目的层级、临时性与原有效期。确实适合长期使用时，非临时条目执行“确认沉淀”，临时条目通过“改为长期偏好”明确确认新的长期取值。不希望保留时删除；“高级管理”中的“清理失效记忆”处理失效记录。
4. 在问题表单勾选“使用已有记忆”可只读取适用条目；再勾选“记住新的偏好”，本次输出结束后才从问题要求中后台提取候选，用于后续任务。当前 `instruction` 直接参与本次生成，不必先存成记忆。学习依赖读取，当前没有“只写入、不读取”的任务模式。关闭读取后两个行为均不执行；手动添加、纠正和删除仍是独立的管理操作。
5. 新用户的两个选项默认关闭，选择保存在当前浏览器。旧版已启用“使用并更新我的记忆”的浏览器保留原有读取与学习选择。一个连续任务使用同一会话；新一轮独立交流进入“我的偏好”→“高级管理”，点击“开始新会话”。刷新或反复提交同一轮要求不会增加独立会话数；开始新会话只排除其他会话的临时条目，未过期的非临时近期偏好仍可使用。
6. 生成后展开解答区域的“来源与详情”→“本次使用的记忆”，查看此回答的历史快照。它不读取最新记忆库冒充历史；未启用、已启用但无适用条目、旧回答缺少快照记录会分别提示。
7. 在“我的偏好”中展开“偏好更新记录”，查看最近沉淀任务。失败后可按服务端允许的状态重试，未完成任务可取消；如果取消前已完成写入，页面会如实提示，需在记忆列表纠正或删除。条目的“详情与来源”显示独立会话晋升进度，并区分自动沉淀与人工确认；任务标识和调用用量在“查看任务详情”中按需查看。
8. 在“我的偏好”→“高级管理”中展开“记忆文件 · 查看与调试”，查看私有目录、索引和每条文件状态；文件标识和路径位于各条目的“文件详情”。点击“查看 / 编辑 Markdown”或“下载文件”。在页面编辑时只修改“记忆内容”正文，点击“保存并导入”；在本地编辑器修改后，先“刷新文件状态”，再“导入本地修改”。
9. 在解答的“来源与详情”→“高级 · 运行与检查记录”中打开“查看记忆注入记录”，或“下载注入记录 Markdown”，核对当前任务的实际请求。它和“本次使用的记忆”侧重不同：后者展示 Answer 固定快照，前者展示当前 job 各次请求中的记忆片段。

不勾选记忆时，原有文字、视频和 MiMo TTS 流程仍可使用。手动填写记忆和任务中的自动提取均可能产生少量回答模型用量；管理已有条目无需调用模型。

本轮记忆入口是网页与 API，CLI 未新增记忆开关或管理命令。CLI 对已有 Answer 生成视频时仍保留它的历史快照。

## 记忆文件与受控编辑

默认位置为 `runs/current/private/memory/`；指定 `private_dir` 后随私有目录移动，不需要额外配置文件路径。

```text
private_dir/
├── memory.sqlite3              # 条目与后台任务的提交依据
└── memory/
    ├── MEMORY.md               # 条目索引与文件状态
    ├── entries/
    │   └── memory_<id>.md      # 每条记忆独立保存内容、层级和证据
    └── snapshots/
        └── job_<id>.md         # 此任务的冻结快照和逐调用记忆投影
```

索引和条目文件帮助查看“记住了什么、依据是什么、当前在哪一层”；任务文件帮助核对“这次构造的模型请求中包含哪些记忆”。文件格式便于阅读、比较和调试，条目仍彼此独立，不汇总成一段用户画像。

**SQLite 是唯一提交依据。直接修改或删除磁盘上的 Markdown 不会立即改变生效记忆。** 修改条目文件后需要显式导入；删除生效记忆仍使用网页或删除 API。索引由程序生成，不是可执行的加载指令，也不会作为整段文本送给模型。

编辑只允许改变条目的记忆取值。ID、字段、范围、层级、有效期、支持次数和证据等元数据用于核对原始记录，不能通过改文件伪造；需要晋升时使用已有确认入口。导入按普通纠正规则生成新 ID，保留层级、临时性和原有效期，重新记录对新取值的人工修改证据，不把旧取值的多会话支持转给新值。

文件顶部 `---` 包围的 JSON 元数据和后部“来源证据（只读）”均须保留原样。可编辑区域是 `## 记忆内容` 之后、只读证据标记之前的正文，记忆取值仍限制为 1～300 个字符。文件使用 UTF-8，最多 512 KiB；页面和 API 还限制至 524288 个字符，中文等多字节文本仍须满足 UTF-8 字节上限。原样导入不产生新的纠正条目。

每份条目文件携带原条目版本摘要。导入在同一事务中核对版本并执行纠正：文件导出后若发生了新的观察、晋升、确认、修改或删除，旧文件不能覆盖数据库中的新状态。成功导入计为人工修改，之前已经开始的后台提取不能迟到写回旧结果。无效格式或冲突会明确报错，原数据库记录保持不变。

自动同步通过内容摘要识别已经保存的本地修改，在发布前再次检查文件；检测到尚未导入的编辑时保留它，清理时也保留已修改的旧文件并显示相应状态。同步不会将本地修改偷偷导入。若条目已改变或删除，应先保留自己的修改，再基于最新条目重新编辑；旧文件不具备恢复已删除记忆的权限。

外部编辑器不共享服务内部的文件锁，检查与写入之间仍可能发生同时保存，不能承诺任意多方同时编辑均无冲突。使用本地编辑器时先完成保存，再刷新状态和导入；不要同时从页面和外部编辑器修改同一份文件。需要持续编辑时可先下载副本，编辑完成后通过页面显式导入，版本检查仍由数据库执行。

| 文件状态 | 含义与处理 |
|---|---|
| `current` | 与已提交条目一致，可查看、下载或开始编辑 |
| `edited` | 本地条目文件有未导入修改；核对后显式导入 |
| `stale` | 本地修改仍保留，但其原条目已经变化；保留草稿，基于最新条目重新处理，不能强行覆盖 |
| `deleted` | 库中原条目已移除，本地编辑仍保留供查看；该文件不能导入恢复旧条目 |

刷新文件状态不会替换页面编辑框中的草稿。切换文件前先保存导入，或选择“关闭编辑，放弃页面修改”；后者仅丢弃页面草稿，不删除磁盘上的修改。`MEMORY.md` 和 `.manifest.json` 是系统生成的索引和同步清单，不作为人工编辑入口。

文件写入失败不撤销已经提交的记忆操作。页面和文件状态接口会显示同步错误，可在磁盘可用后再次同步。记忆学习与生成仍以已提交数据库为准，因此“记忆保存成功”和“Markdown 已同步”是两个分别可检查的结果。

## 两层与默认策略

| 项目 | 默认行为 |
|---|---|
| 短期 `short_term` | 新候选先进入短期，默认 14 天有效；非临时条目在有效期内可跨会话使用 |
| 深层 `deep` | 同范围、字段和值获 3 个独立会话支持，或非临时条目由用户明确确认后进入 |
| 临时条目 | 只在原会话使用，不自动晋升；普通纠正仍临时，显式“改为长期偏好”才转为深层 |
| 重复 | 同 `source_id` 重放幂等；同一会话反复表达不增加独立支持数 |
| 冲突 | 当前会话的新要求覆盖旧默认；新值得到足够支持或确认后才替换稳定值 |
| 适用范围 | 默认 `global`；API 可指定范围，在当前会话表达优先后，对应范围优先于全局同字段 |
| 深层有效性 | 不因长期未访问自动到期；可被新确认值替代或由用户纠正、删除 |
| 普通纠正 | 替换为新条目，保留原层级、临时性与到期时间，不借编辑延长短期寿命或自动晋升 |
| 容量 | 最多 200 条，每条最多保留 20 份支持证据；上下文最多 12 条、6000 字符 |
| 来源去重 | 最多 10000 个已处理来源；保存标识摘要和输入摘要，不保存额外原文；满额后拒绝新来源写入，已有记忆仍可读取和管理 |

以上阈值由 `Settings.memory_policy` 配置，默认 3 个独立会话晋升、短期有效期 14 天。条目在写入时、服务启动时及后台约每 60 秒自动清理；管理面板仍提供手动清理。后台队列最多 100 个未完成任务；已取消但模型调用尚未返回的任务也占用此容量。最多保留 200 个终态摘要，优先保留尚待用量结算的记录，其余按时间清理。

首版匹配使用规范化后的字段和取值，不做语义近义合并。例如“先画图”和“先看示意图”是否成为同一取值取决于提取结果；不能把匹配规则描述成已经解决语义归一化。会话计数是工程代理指标，不能自动证明真实人的稳定偏好。

容量清理优先移除临时或证据较少的短期条目，不自动驱逐深层条目；若容量全被深层记忆占用，新写入会失败并提示先删除不再需要的记忆。临时条目如确实需要变成长期偏好，可在页面显式“改为长期偏好”，确认新的长期取值；这与直接按出现次数晋升不同。

## HTTP 入口

所有路径在 `/api/v2` 下，最终字段与约束以 `/openapi.json` 为准。

| 方法与路径 | 请求 | 作用 |
|---|---|---|
| `GET /memory` | 无 | 返回 `entries`、`policy` 和 `learning:{tasks,counts}`，后者包含近期沉淀任务及各状态计数 |
| `GET /memory/documents` | 无 | 同步并读取记忆目录、索引位置与各文件状态 |
| `POST /memory/documents/sync` | 无 | 显式重试文件同步，保留未导入的本地编辑 |
| `GET /memory/documents/{memory_id}` | 无 | 读取条目 Markdown；`?download=true` 下载文件 |
| `POST /memory/documents/{memory_id}/import` | `{"content":"编辑后的完整 Markdown"}` 或 `{}` | 前者导入页面文本；省略 `content` 或设为 `null` 则读取本地文件，检查版本后执行人工纠正，返回条目 |
| `GET /jobs/{job_id}/memory-context` | 无 | 读取该任务的冻结快照和逐调用记忆审计；`?download=true` 下载 Markdown |
| `GET /memory/learning/{job_id}` | 无 | 查看指定后台沉淀任务摘要 |
| `POST /memory/learning/{job_id}/retry` | 无 | 对允许重试的失败任务重新排队；总尝试最多 3 次 |
| `POST /memory/learning/{job_id}/cancel` | 无 | 取消尚未完成的沉淀；若已原子提交，则返回已完成状态，不撤销已写入条目 |
| `POST /memory/observations` | `text`、`session_id`、`source_id`、可选 `scope` | 从用户表达提取有原句依据的候选并入库 |
| `POST /memory/{memory_id}/confirm` | 无 | 明确确认非临时条目，进入深层 |
| `PATCH /memory/{memory_id}` | `{"value":"新取值","confirm_long_term":false}` | 以新 ID 纠正并替代旧条目，保留层级、临时性与有效期；省略布尔字段同样默认为 `false` |
| `DELETE /memory/{memory_id}` | 无 | 删除活动记忆库中的条目和附属证据 |
| `POST /memory/cleanup` | 无 | 执行清理并返回统计 |

文件状态接口返回 `root`、`index_path`、`index_content`、`entries` 和 `error`。其中每项包含 `memory_id`、`path`、`status`，仍有生效记录时另有字段和层级；`error` 非空表示镜像同步未完成，不等于数据库中的记忆未保存。读取单个文件返回 `{memory_id,content}`，下载参数返回 Markdown 附件。

导入错误包括：`memory_document_invalid`（422，编码、大小、格式或只读部分被修改）、`memory_document_conflict`（409，基准版本过期或原条目已删除）、`memory_document_not_found`（404，镜像不存在）、`memory_document_unavailable`（503，文件无法读取）。过期或已替代等不可纠正记录仍按原记忆接口报错。冲突和失败均不自动重试写入，不将被拒绝的文件内容用于后续生成。

自然语言记忆输入示例：

```json
{
  "text": "以后解释几何题时，我希望先展示示意图，再列公式。",
  "session_id": "lesson-20261106-a",
  "source_id": "observation-20261106-a1",
  "scope": "geometry"
}
```

`source_id` 标识一次用户表达：网络重试沿用同一个 ID，不为同一来源不断换新 ID；同一来源 ID 不能改绑不同输入。`session_id` 标识独立交流，不是用户账号。当前系统没有多用户身份与访问控制，不可据此宣称不同用户的数据已经隔离。

明确将新取值确认为长期偏好时，PATCH 传 `{"value":"以后都先画图","confirm_long_term":true}`，条目进入深层并清除临时性和到期时间。过期或已被替代的条目不能继续纠正。普通纠正不继承旧取值的多会话支持次数，避免把旧证据算作对新取值的认可。

API 用户表达最多 12000 字符，网页记忆输入框最多 4000 字符，提取最多 5 个候选。首版复用回答模型的连接和凭据，单独限制输出预算、关闭 thinking、禁止提取重试，并将单次等待限制在 20 秒以内；服务商需支持当前 Chat Completions 配置。管理 API 的模型失败返回明确错误，不把失败显示为已保存。

新建文字／双输出任务时，可以在 `POST /generations` 的顶层传入可选 `memory`：

```json
{
  "output_mode": "both",
  "memory": {
    "session_id": "lesson-20261106-a",
    "scope": "geometry",
    "learn": true
  },
  "source": {
    "type": "inputs",
    "inputs": [{"type": "text", "text": "给定 a=(3,2)、b=(2,0)，计算 a 在 b 上的正交投影。"}],
    "instruction": "解释投影系数、投影向量，并验证残差正交。这次请先画示意图。"
  }
}
```

`learn: true` 表示受理时读取已有记忆，并登记一个等待本次生成结束的后台任务；`false` 只读取已有记忆。省略整个 `memory` 则不启用。直接生成 Answer 的接口同样支持可选记忆参数。复用已存在 Answer 的 `source.type=answer` 请求不接受新的 `memory` 参数，视频使用该 Answer 的历史快照，不重新提取或替换为最新画像。

## 后台沉淀与恢复

```text
受理任务，冻结已有记忆 → learn=true 登记 waiting
  → 主任务进入终态，且已发布完整 Answer（包括文字成功、视频失败的 partial）
  → queued → 单个后台 worker 提取 → completed / failed / skipped
```

没有发布完整 Answer 的任务取消沉淀。后台 worker 领取任务前优先让出前台生成队列；已在执行的沉淀使用独立线程和独立预算，不占用正文的调用、token 或 deadline。默认每次尝试最多 1 次调用、20 秒、16000 token；`memory_learning_timeout` 可调但不超过 20 秒，`memory_learning_max_tokens` 配置独立 token 上限。没有自动 provider 重试；失败需手动重试，连同首次总共最多 3 次。

服务重启后，对 `waiting` 根据父任务及 Answer 是否存在重新对账；`queued` 保持可执行；执行中的任务若未提交记忆则转为失败，需手动重试，不自动重放可能已计费的调用。来源已原子写入的任务恢复为完成，不重复增加证据或晋升次数。若历史写入缺少效果记录，新增／强化统计显示未知，不猜测效果。

提取结果写入时在同一 SQLite 事务内检查取消状态与人工修改版本。确认、纠正、删除等人工修改发生后，旧提取结果不能迟到写回；用户可按提示决定是否重试。取消与提交竞争时，以原子事务结果为准。

任务摘要提供 `state`、`attempts/max_attempts`、`can_retry/can_cancel`、`entry_ids/promoted_ids`、新增／强化／晋升计数及 `counts_known`、安全错误、时间、累计 `usage`、`usage_unknown` 和 `attempt_history`。前端只展示近期 20 项；有活跃任务时每 5 秒刷新，最多 120 轮，连续 3 次读取失败则暂停。手动刷新或新的生成结束可重启观察。暂停前端刷新不取消后台任务，刷新不会覆盖正在编辑的条目或历史回答快照。

后台提取用量在沉淀任务中按尝试累加，不计入主生成任务的 `usage`。服务中断等情况可能只知道已调用而没有完整 token 回报，此时用量为未知或不完整，不能当作零成本。网页手动“生成记忆”仍是直接提交并等待提取的独立管理操作，不经过父生成任务等待阶段。

取消后仍可能收到已发出调用的用量，系统会保留结算记录并只记账一次；记录不会被后续大量短任务提前挤出历史。若服务重启后无法取得该回包，则保留未知用量状态并恢复普通历史清理，不补写为零，也不自动重发调用。

## 快照与输出边界

已有记忆在任务受理时冻结，`learn:true` 和 `learn:false` 的读取时点相同。排队期间新增或修改的记忆不改变已受理任务的快照；当前 `instruction` 仍直接生效且优先于快照。本次后台提取发生在结果发布后，新记忆只影响随后受理的任务，不回填本次回答。

Answer 保存生成时的 `memory_snapshot`。人工修改 Markdown 产生新版本时继承快照；随后生成或重试视频沿用对应 Answer 的快照。这样文字和画面不会因为用户中途修改偏好而使用不同记忆。

任务受理和进入终态时自动写入 `memory/snapshots/<job_id>.md`。运行中可通过 `/jobs/{job_id}/memory-context` 查看当前任务记录，也可按需从已保存记录重建文件。复用 Answer 和单独视频任务使用对应 Answer 的原快照，不能用今天的记忆库补写成历史状态。

审计的 `snapshot_state` 区分 `recorded`、`disabled` 和 `unknown`。旧任务或旧 Answer 根本没有保存快照字段时，结果为未知；不能把缺少历史记录解释成当时明确关闭了记忆。

审计按实际调用记录列出角色、尝试次数、HTTP 状态，以及请求中 `user_memory`、`recent_user_memory` 的真实投影，并解释快照条目是否出现在该调用中。没有请求记录时不会凭角色规则推断“已经注入”。`request` 事件只证明客户端构造了请求；HTTP 成功也不证明模型遵守了偏好。该导出只提取记忆相关内容，不复制题目材料、生成正文或凭据。

完整审计快照保留策略版本、捕获时间、会话、条目 ID、层级与更新时间。模型收到的是从该快照生成的稳定投影：`user_memory.deep` 含深层条目的 `field/value/scope`；`recent_user_memory` 含近期条目的相同字段以及 `temporary`。ID、时间戳、会话账本和证据不进入该投影；不重新选择、总结或合并记忆。回答与内容检查过滤已知的 `visual.*` 字段，视频角色保留，未知自定义字段保守保留；材料读取和记忆提取不注入历史偏好。因此，快照中的条目不一定进入每个阶段的提示词。

当前要求优先于历史记忆，记忆不得改变题目条件、数学结论、材料来源和安全约束。回答与视频模型收到有界 JSON 上下文；实际表达是否遵守偏好仍取决于模型和可信模板能力。现有模板固定的配色、字体、布局不支持任意用户定制，不能把“视觉偏好已进入规划”描述为“所有视觉偏好已执行”。

## 提示词顺序与缓存统计

系统规则和 schema 保持固定；用户载荷按“深层记忆 → 共享材料／固定回答与大纲 → 近期记忆 → 当前 instruction、场景与反馈”排列。没有记忆时省略记忆段。场景调用优先保留同角色、同一 Answer 下的共享前缀，不把场景修复反馈放到大纲前。稳定层内按固定字段及条目顺序序列化，不对整个载荷全局排序。来源引用 ID 仍保留，重新上传相同内容不保证跨任务前缀相同。

解答的“来源与详情”→“高级 · 运行与检查记录”展示任务 `usage` 中的缓存统计：

| 字段 | 含义 |
|---|---|
| `cached_input_tokens` | 有效回报的缓存输入 token 合计；全部未回报时为 `null`，合法回报 `0` 表示已知零命中 |
| `cache_reported_calls` | 有效回报缓存用量的调用数，结合 `model_calls` 显示覆盖情况 |
| `cache_accounted_input_tokens` | 仅这些有效回报调用的完整输入 token 合计，作为比例分母 |

命中比例只按 `cached_input_tokens / cache_accounted_input_tokens` 计算；分母为零时无法计算。若仅部分调用回报，页面注明“已报告输入中的命中比例”，其他调用仍未知，不能用整个任务的 `input_tokens` 补分母或当作零命中。旧记录缺字段、无效或相互矛盾的用量也按未知处理。缓存 token 仍计入原有完整输入预算。

同字段冲突先在快照中选出有效值。因此，临时要求替代某个深层默认时，该默认会从前置深层段移出，公共前缀仍可能变化。重复支持同一取值不会仅因更新时间或证据数量变化而改变模型投影；容量选择也不再按这些变化重新排列无关字段。

共同前缀稳定是可验证的输入性质，不等于服务商必然命中缓存。[本轮 MiMo 合成对照](../../testresult/memory-cache-20261106/cache-run/报告.md)共调用 6 次，其中当前结构第 3 轮报告 6592 / 6649 个输入 token 命中，另外 5 次未知。该样本不能证明总体提速或成本下降；已有检查结果和场景续跑的应用层复用也不等同于服务商提示词缓存。

## 失败、保存与删除

提取只根据用户原话，不读取上传教材为用户事实，也不以系统答案、观看次数或渲染成功推断用户掌握了知识。后台队列满或登记失败时，主任务可继续使用已有记忆，并显示未排入沉淀的警告。后续提取失败在沉淀列表中明确显示，不将已完成正文改为失败，也不声称偏好已经保存。任务记录保留实际快照及提示，用于解释本次使用了哪些信息。

SQLite 保存在 `private_dir/memory.sqlite3`，数据库文件不应提交到仓库。删除移除条目正文与附属证据，但保留不含原文的来源摘要，以防重放同一旧来源重新生成已删除条目。删除与清理影响后续检索；已发布的 Answer、视频、诊断以及备份中的历史快照保持原样，不属于本接口的全量擦除范围。分享历史诊断前需检查其中的个人信息。

`memory/` 中的条目原句、证据和历史任务快照也属于私有运行数据，不进入源码包。删除库中条目后，未修改的对应镜像可被同步清理；未导入的本地编辑及历史任务快照会保留，用户需要自行决定是否保存或删除这些文件。文件格式便于检查，不代表会跨设备自动同步或已加密。

后台任务在完成、取消、跳过或重试耗尽后清除队列中的用户原文；仍可重试的失败任务保留必要输入，直到重试完成、耗尽或历史清理，不承诺按天自动删除失败原文。失败状态不能直接取消；重新排队后可按服务端允许状态取消。队列的去原文化不删除原主任务记录、Answer 或备份中的用户表达，不等同于全量隐私擦除。
