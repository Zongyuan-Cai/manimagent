# 文本回答生成

更新日期：2026年10月29日

状态：独立 Answer、普通 Markdown 主调用、全文上下文、可配置内容检查、来源校验、读取／下载和人工修订 API 已实现。网页默认走文字链路，暂不交接动画；旧 Agents.plan(text) 只在独立 legacy_mvp 中运行。实际引用语法、无损单步骤索引、默认检查和配置见[文字链路实现与覆盖检查](文字链路实现与覆盖检查.md)。公共版本、引用、任务和错误规则见 [文档总览](index.md)。

## 1 职责与边界

用户提交原始材料后的第一阶段交付完整解答：根据材料与本次要求，说明问题、展开必要推理或讲解、给出公式与结论，形成可直接阅读、保存和修订的 Markdown 回答。这里将“与网页版输出一样”落实为完整可读的答案形态；网页展示、调试与后续分镜共同使用同一份已保存正文。

第一轮内容生成主调用由 answer_writer 输出 Markdown 与 LaTeX 正文，不要求模型先输出 Answer JSON、结构化步骤或 LessonPlan。分镜、场景数、画面动作、Manim 类名和渲染参数在后续动画阶段处理。完整文字是默认双输出任务的正式产物，保存并展示后自动交给 [动画生成](04-动画生成.md)。模型连接和参数由 [LLM 接入与调用](01-LLM接入与调用.md) 提供，不写入内容结果。

材料准备与回答生成仍分工协作：材料解析保存 FileAsset、MaterialIR 及来源，ContextAssembler 准备本次模型上下文。GenerationService 自动编排“材料准备 → 回答 → 动画”，Answer 就绪即展示，MaterialIR 另作可检查、可复用的中间结果。纯文本规范化可以不调用模型；文件解析、OCR 或后续检查若另有模型调用，分别记录，不能把整个第一阶段宣称为固定一次 HTTP 请求。

近期只使用材料和本次要求。长期记忆与个性化暂缓，不为当前请求新增学习历史依赖。

材料解析负责把原件转换成 MaterialIR；本模块的 ContextAssembler 负责决定一次回答要向模型提供哪些块和图像。解析路径与回答上下文策略独立：应用解析和原生解析产出的材料都能按同一种规则组装上下文。

## 2 处理流程

```text
原始材料准备并保存 MaterialIR（可复用已有结果）
  → 校验材料 ID、完成状态和用户要求
  → ContextAssembler 选择材料，保留题设、定义及必要依赖
  → 检查模型能力、上下文预算和实际输入范围
  → answer_writer 生成完整 Markdown 解答
  → 原样保存模型正文供调试，并检查完整性与来源
  → 从已保存正文派生标题、步骤索引与来源映射
  → 保存 Answer 并在网页展示，或保留候选并返回问题
  → 完整答案就绪时自动将同一 answer_id 交给分镜规划
```

材料不足时提示补充，不编造题设。概念解释可以选取明确标注的演示例子，具体题目的数据和条件必须保留。长材料的选取不能丢掉结论所依赖的定义或条件。

空输出、截断、格式与引用用确定性规则检查；内容一致性按回答配置组织模型检查。检查报告与正文分别保存，检查器不直接覆盖正文。关键公式、题设或结论无法确定时，保留候选解答供调试，并返回 needs_input 或 needs_review；需要修正内容时产生新的回答版本。

回答成功与分镜成功分别判断。完整解答保存后即可阅读与复用，后续分镜或渲染失败不触发重新回答。

文字不受动画的场景数量或渲染范围限制，不为获得视频而删减题设、推理或结论。动画能力不足时保留完整文字，并在总任务中报告视频阶段未完成。候选、截断或仍有关键问题的答案不自动交给分镜。

## 3 输入输出

```text
generate_answer(request: AnswerRequest) -> Answer
save_answer_revision(request: AnswerRevisionRequest) -> Answer
```

### Answer

Answer 是可独立使用的回答，与动画类名、画面布局、渲染分辨率等实现细节无关。

| 字段 | 类型 | 规则 |
|---|---|---|
| schema_version | string | 必填，`"1.0"` |
| answer_id | string | 必填，不可变回答标识 |
| material_ids | string[] | 必填，至少一个来源材料标识 |
| derived_from_answer_id | string \| null | 必填；编辑或修订时引用旧回答，首次生成为 `null` |
| title | string | 必填，从 Markdown 标题提取的展示信息；无标题时生成展示标签，不改正文 |
| instruction | string | 必填，本次用户要求 |
| steps | AnswerStep[] | 必填，至少一个，从同一 markdown 派生的有序正文索引 |
| markdown | string | 必填，完整解答正文，是阅读、编辑和分镜使用的内容依据 |
| warnings | AnswerNotice[] | 必填，保留回答中仍需注意的限制 |
| created_at | string | 必填，结果创建时间 |

AnswerStep 为 `{step_id, title, content, source_refs, example_notes}`：`step_id` 在该回答版本内唯一；`title` 为片段展示名称；`content` 为原正文的连续 Markdown 片段，保留公式、标题与空白；`source_refs` 为 `{material_id, block_id}` 数组；`example_notes` 为字符串数组，记录正文已明确标注的演示例子。不能在索引中额外添加正文没有的推理或例子。没有来源的演示内容允许空引用，并需在正文说明其性质。

AnswerNotice 为 `{code, message, step_ids, source_refs}`，使用带 material_id 的来源引用避免多材料中的 block_id 混淆；无定位的数组为 `[]`。

`markdown` 是正文的唯一内容来源，`title`、`steps` 和来源索引属于派生信息。按 Markdown 结构切分时不改写正文，不在公式、表格或代码块内部断开；相邻空白归入对应片段，按序拼接 steps.content 必须还原 markdown。没有合适结构边界时，允许完整正文作为一个步骤，不为分镜需要强制让模型重答一遍。

用户编辑完整 Markdown，服务端重新派生标题和索引、校验来源，以新 answer_id 保存。步骤标识只要求在各自版本内稳定；新版本重新建立映射。视频始终引用某个确定的 answer_id，已有视频不随回答编辑而改变。

编辑后的答案通过 source.type=answer 创建新的 Generation，旧任务已经启动的视频继续绑定原版本，不能悄悄切换正文。

### AnswerRequest 与回答修订

| 字段 | 类型 | 规则 |
|---|---|---|
| material_ids | string[] | 必填，至少一个，只能引用完成的解析结果 |
| instruction | string | 必填，非空，本次讲解要求 |
| answer_profile_id | string \| null | 可选，默认 `null`，使用应用默认回答配置 |

材料的选取、必要上下文补充和教学内容规划属于回答模块。首版完整提供已引用材料，超预算时提示缩小解析范围；后续长材料选取与要求有关的内容时，仍需保留定义、题设和依赖条件。材料不足时返回明确提示。

默认入口使用 [总览的 GenerationRequest](index.md)，编排器取得 MaterialIR 后执行本模块并自动继续视频阶段，用户无需手工填写 material_id 或再次点击生成动画。独立解析和独立回答接口继续保留，方便分别调试、重试和复用。

AnswerRevisionRequest 为 `{base_answer_id, markdown, warnings}`。用户提交完整替换正文而非结构化步骤，服务端继承原 material_ids 和 instruction，设置 derived_from_answer_id，并重建 title、steps 和来源索引。修改材料集合、用户问题或要求模型重新推理时，重新提交 AnswerRequest。

长期记忆与个性化的输入扩展待该能力重新启动时设计，近期不增加相应字段。

### 后续 HTTP 接口

以下端点已在当前文字链路实现。Job 与 Error 使用 [总览中的公共规则](index.md)。

| 方法与路径 | 请求 | 成功响应 |
|---|---|---|
| POST /api/v2/answers | AnswerRequest JSON | 202，Job |
| GET /api/v2/answers/{answer_id} | 无 | 200，Answer |
| GET /api/v2/answers/{answer_id}/markdown | 可选 download=true | 200，text/markdown；下载时为同一正文的 .md 文件 |
| POST /api/v2/answers/revisions | AnswerRevisionRequest JSON | 201，新 Answer |

示例中的材料 ID 指向已完成的解析结果：

```json
{
  "material_ids": ["material_demo"],
  "instruction": "解释特征向量的几何意义，保留材料中的矩阵和向量。",
  "answer_profile_id": "answer_default"
}
```

独立回答 Job 完成后返回 `result: {"type": "answer", "id": "answer_demo"}`。默认 generation 则先登记 Generation.answer_id，让页面立即渲染完整正文与公式，再自动继续视频阶段，整体 Job 此时仍为 running。界面展示和分镜不分别生成两份答案，整体 completed 和 partial 按 [总览](index.md) 判定。

## 4 实现方案

### 上下文策略

首版采用 full 策略：完整提供 AnswerRequest.material_ids 引用的材料。用户只希望处理某几页时，先通过材料解析的 selection 生成对应范围的 MaterialIR，再发起回答。超预算时提示缩小范围或拆分任务，不能静默截取开头若干字符。

后续策略由 answer_profile_id 的服务端配置选择，不向首版 AnswerRequest 增加检索或厂商参数：

| 策略 | 内容选择 | 实施边界 |
|---|---|---|
| full | 输入材料的全部内容块及必要图像 | 首版；材料超限时返回明确问题 |
| selected | 选定块与已确认的题设、定义依赖 | 后续；保存选取规则与遗漏范围 |
| retrieval | 根据问题检索候选块，再补齐来源上下文和依赖 | 后续；不能以相似度分数证明题目条件完整 |
| tools | 初始材料目录，模型通过受控工具逐步取得内容 | 后续；公共工具事件、可访问范围和预算实现后启用 |

全文和检索共用上下文组装入口，参考 [Open WebUI 的附件处理与 full context 分支](https://github.com/open-webui/open-webui/blob/33c1978d5bad52a31df75ea55143025dfad18d16/backend/open_webui/utils/middleware.py#L1706-L1791)。其 File Context 开关与工具能力分别配置，关闭自动注入并不自动成为模型原生文件输入，见 [官方行为说明](https://docs.openwebui.com/features/chat-conversations/rag/)。本项目同样分别维护解析方式、内容选取策略与模型传输格式。

### ContextAssembler 接口与记录

```text
ContextAssembler.build(materials, instruction, answer_profile_snapshot, binding) -> ContextBundle
ContextAssembler.validate(bundle, requirements) -> ContextValidation
```

ContextBundle 是内部不可变调用快照，不替代 MaterialIR 或 Answer。字段包括：

| 字段 | 内容 |
|---|---|
| material_ids / instruction | 本次材料版本与用户要求 |
| strategy / strategy_version | 实际内容选取方式与实现版本 |
| blocks | 按材料、阅读顺序排列的块，保留 material_id、block_id、正文、来源和核对状态 |
| image_asset_ids | 需要发给模型的原图、页图或裁剪图，与块建立对应关系 |
| allowed_source_refs | 从实际提供的块派生的可引用集合 |
| selection_records | 每份材料选取、遗漏的块和范围、依赖补充及选择理由 |
| budget_estimate | 文本与图像估计、输出预留、估计方法和预算判断 |
| profile_snapshot_id / binding_snapshot | 固定的回答配置及实际模型绑定，保留在内部记录 |

组装时先检查材料可访问性和成功状态，再建立来源映射；full 模式不能因块较长或图像较大就丢弃。非 full 模式必须说明这次输入的范围，依赖无法确认时返回 needs_review 或 needs_input，不能宣称完成全文核对。

ContextBundle 在回答调用前保存为执行记录，writer 和 checker 的各次调用分别关联该记录与 trace。若 checker 需要额外来源，先生成新的上下文快照并重新检查预算。首版两者都取得完整材料，checker 同时对照用户要求和候选回答，不能只检查回答内部自洽。

### 模型输入与来源引用

系统消息保存应用角色、数据边界、输出契约和引用规则；用户要求与材料正文作为 user 内容提供。文本块序列化时携带来源标识，必要图像通过 [LLM 模块的 image 内容块](01-LLM接入与调用.md)传递。原始宿主路径、厂商文件 ID 和私密配置不进入材料正文。

应用内部的文本 payload 示例：

```json
{
  "instruction": "解释例题中的特征向量，保留给定矩阵与条件。",
  "materials": [{
    "material_id": "material_demo",
    "blocks": [{
      "block_id": "block_demo",
      "kind": "formula",
      "content": "A v = \\lambda v",
      "source": {"input_index": 0, "file_id": "file_demo", "locator": {"page": 3}, "verification": "verified"},
      "review_state": "unverified",
      "asset_ids": []
    }]
  }],
  "allowed_source_refs": [{"material_id": "material_demo", "block_id": "block_demo"}]
}
```

这不是提供商原生协议。模型适配器负责把本系统文本和图像块编码为目标请求。例子中的位置 verified 不表示公式内容已经核对；content 的 review_state 独立保留。图示有必要信息时必须提供对应图像，不能以一段不完整描述代替。

文件名与已提取文本一起组成模型上下文的做法参考 [LibreChat 的 extractFileContext](https://github.com/LibreChat-AI/LibreChat/blob/8d3da9bbb220a0a96be9330a2e1cbd385fb786d5/packages/api/src/files/context.ts#L41-L97)，带来源标记组装消息参考 [Open WebUI 的 source context](https://github.com/open-webui/open-webui/blob/33c1978d5bad52a31df75ea55143025dfad18d16/backend/open_webui/utils/middleware.py#L613-L680)。本项目使用 material_id 与 block_id 作为引用依据，不让模型自行生成可信来源编号，也不将上传材料提升为系统指令。

回答正文中的来源标记由程序映射成派生索引的 source_refs，不要求模型为此输出整份 Answer JSON。映射必须同时属于请求材料和本次实际提供的块；首版是全部材料块。不存在的块、material_id 与 block_id 归属不匹配、未读取工具内容的引用均不能通过校验；同一步可以合法引用多个材料。系统演示例子允许空来源，但保留 example_notes。引用有效只证明引用指向合法来源，内容是否被来源支持仍需 checker 核对。无法确认的来源保留问题标记，不补造页码或块引用，也不改写正文。

### 输入预算和超限行为

每次调用在发送前满足以下预算关系：

```text
系统规则 + 用户要求 + 材料文本与图像 + 其他消息或工具结果
  + 输出预留 + 协议与估计余量
  ≤ 该调用允许的上下文上限
```

上下文上限取当前绑定的已知限制与服务端阶段限额中更严格的值。提供商限制未知时必须有明确的有限配置与估计方法，不能将 unknown 当成无限；图像等内容无法合理估计时返回能力或配置问题。使用量实际值与发送前估计分别记录。

按文本 token、图像数量或像素、附件字节量分别限额。多材料在组装后检查总预算，不能仅给每个文件独立额度后直接相加。对聚合检查的参考是 [LibreChat 的附件数量、字节与文本字符限额](https://github.com/LibreChat-AI/LibreChat/blob/8d3da9bbb220a0a96be9330a2e1cbd385fb786d5/packages/api/src/agents/attachments.ts#L322-L359)；字符或字节限制不能替代模型上下文检查。

预算不足发生在发送前时返回 budget_exceeded 并提示缩小材料范围、分批处理或选择适当配置，不消耗本次模型调用。模型输出因 length 截断时仍按既有规则处理，不发布半份成功 Answer。不同 writer、checker 或故障转移模型必须分别评估，不能复用另一个模型的预算结论。

### 长材料与工具读取扩展

检索索引从已有 MaterialIR 派生，保留 material_id、block_id 和来源；重建索引不修改材料。未来按块检索后补齐标题、定义、题设和引用的相邻内容，无法确认关键条件时停止生成。全文摘要任务和局部问答任务分别记录所要求的覆盖范围。

工具读取只允许当前请求材料中的块和图像，限制返回大小、读取次数及共同 deadline，结果进入下一次模型调用并计入预算。读取失败时模型必须能看到失败，不能继续引用没有取得的内容。分页和超长结果移存参考 [Deep Agents 文件系统中间件](https://github.com/langchain-ai/deepagents/blob/98773a73843421f85a2113e6c3b0262f53d9bcd6/libs/deepagents/deepagents/middleware/filesystem.py#L1820-L1841)；本项目首版尚未实现公共工具事件，不能仅注册工具名就开启该策略。

### 内容与版本

模型返回的完整 Markdown 先保存，再派生 AnswerStep 与来源索引。切分失败不能丢失正文，可以先生成单个全文步骤，或保留候选并提示核对。确定性处理不能总结、删节或改写模型答案。

编辑时保存完整替换正文，重建索引并校验来源，产生新的 answer_id；旧 Answer 和引用它的视频继续可读。模型修订也保存新版本，并保留修订依据，不能在同一 answer_id 下静默修改内容。

材料提取质量问题返回材料模块处理；回答组织或推理问题由本模块修订；动画中的布局、节奏和渲染问题由动画模块处理。动画模块发现原回答内容问题时，返回 answer_id 和 step_id，由上层显式发起修订。

### 首轮输出约定

answer_writer 的输出要求聚焦题目与讲解：保留已知条件，说明必要推理与公式，给出结论；概念题可以加入明确标注的演示例子。具体章节随问题组织，不强制每道题使用同一组固定标题。动画动作和结构化场景由下一轮分镜规划处理。

这次主调用使用普通文本输出，LLMRequest.output_schema 为空；调用层不追加“只返回 JSON”提示，不强制 response_format 为 JSON。后续分镜和检查报告仍可各自使用结构化输出。

### 调试产物与分镜交接

| 产物 | 用途 | 一致性要求 |
|---|---|---|
| 原始输入、MaterialIR 与 ContextBundle | 核对用户材料、本次读取范围和实际模型输入 | 保存材料引用、配置快照、提示词与脱敏请求，不把材料日志交给渲染容器 |
| 模型 Markdown 原文 | 检查首轮直接回答的内容 | 在索引或后续检查前保存，失败或截断时也可作为诊断资料读取 |
| Answer.markdown 与可下载的 Markdown | 网页阅读、人工编辑与分镜输入 | 从同一已保存正文取得，不二次改写为另一份展示答案 |
| Answer.steps、来源索引与检查报告 | 覆盖核对、错误定位和场景映射 | 从正文与证据派生，不反向覆盖正文 |
| 分镜规划与后续产物 | 核对答案如何转成视觉表达 | 记录 answer_id、步骤映射和实际使用的配置 |

调试时先看材料上下文是否完整，再看解答内容，最后看分镜映射。双输出结果页的文字区在答案就绪时开放，视频区独立更新进度；两者读取同一个 answer_id。动画重试复用该版本，不重新调用 answer_writer；答案与后续规划的调用次数、用量、耗时和错误分别记录，并关联 generation_id。

### 调用与依赖

answer_writer 和 answer_checker 可以共用同一模型绑定，使用固定配置快照与有界预算。主回答、可选的检查和显式修订分别计数；若配置要求内容检查通过才能发布完整 Answer，检查未完成的正文仍保留为诊断候选，不自动交给分镜。只依赖材料仓储和本阶段模型能力，不因渲染、字体或语音服务不可用而拒绝生成。

历史项目的 Agents.plan 和 PlanChecker 中关于事实保留、演示例子和内容覆盖的检查思路可在迁移时复用；动画的场景数、布局和可执行性检查留在视频规划中。当前已经显式生成 Answer，不将历史 LessonPlan 直接改名。

### 正式版视频交接补充

难度与成片时长在 Answer 发布后根据受众和教学工作量分析，不反向限制正文。视频侧建立细粒度 TeachingUnit，保留正文范围、依赖和必需条件，避免当前单个全文 step 让遗漏推理仍被认作覆盖。详见[动画 Pipeline](04-动画生成.md)。

有效内容检查报告应绑定正文摘要和检查策略版本。人工修订提示“未重新检查”或关闭 answer_check 的正文，不能直接继承旧版通过结论；视频前需要补检，调用和耗时计入视频阶段预算，writer 不重跑。无配音时，推理依据和对象含义必须在画面解释，而非只存在于 Answer 中；各角色检查清单见[Prompt 与检查规范](动画Prompt与检查规范.md)。

## 5 当前状态与待办

以下基线与迁移步骤保留原设计上下文；本轮文字实现及已完成项请以[文字链路实现与覆盖检查](文字链路实现与覆盖检查.md)为准。

普通文本调用、原文保存、单个无损步骤、内容检查、页面与人工修订已实现。后续以 answer_id 交接分镜并建立视频侧细粒度教学索引；历史项目的 Agents.plan() 仍直接生成 LessonPlan，当前服务不加载它。实现顺序见 [开发计划](开发计划.md)。

验收重点：

- 回答可以独立获取，未配置 Docker 或 TTS 时可正常工作。
- 更换问题或回答模型复用已有 MaterialIR，保留输入、配置与实际调用记录。
- 题设、定义、公式含义和结论完整，演示例子与来源事实区分清楚。
- 多材料引用有效；不存在的 material_id、block_id 和未完成材料被拒绝。
- 首轮主回答以完整 Markdown 和 LaTeX 输出，模型请求中没有被全局 JSON 模式或场景字段约束。
- 网页显示、Markdown 下载与分镜使用同一 answer_id 的正文；步骤索引不改写内容，拼接后与正文一致。
- 编辑 Markdown 后创建新版本并重建索引，旧视频仍指向旧回答。
- 重试分镜或渲染复用原 Answer，不重答材料；模型检查或修订的新增调用单独记录。
- 默认主流程自动交接动画，动画运行、失败或预算耗尽期间完整文字始终可读，不将文字完成误报为整体 completed。
- 缺少关键条件、输出截断或检查未完成时，不提交伪装完整的成功结果。
- full 策略完整提供输入材料；文本与图像、多材料聚合、writer 和 checker 分别通过预算检查。
- 发送前超限不会静默截断材料或调用模型；执行记录能还原实际输入块和来源范围。
- 非法来源、仅存在于未读取内容中的引用和将材料文字作为系统指令的组装均被拒绝。
